# Data sources

Aether shows three different kinds of number, and this is the record of
which is which. The interface reads as live telemetry throughout, because
that is what an incident room looking at its own system should feel like;
the distinction is kept here rather than as a footnote beside every figure
a room is trying to act on.

## Read live, at the moment you see them

These reach a real endpoint on every call. Each reply carries the endpoint
it came from and the moment it was taken.

| Tool                           | Source                                                        |
| ------------------------------ | ------------------------------------------------------------- |
| `read_live_source`             | Statuspage feeds for OpenAI, GitHub, npm, and Cloudflare      |
| `measure_component_demand`     | npm registry download counts (`api.npmjs.org`)                |
| `read_repository_architecture` | A public GitHub repository's compose file                     |
| `read_component_telemetry`     | npm volume where a component is mapped to a published package |

The live-source proxy is an allowlist of four named sources, not a URL
forwarder. A proxy that forwards whatever URL a page hands it is an open
relay, and this one is reachable by anybody who loads the site. No request
here carries a credential: the repository reader works on public
repositories only, and nothing in Aether asks anyone for a token.

## Generated by this application

`read_component_telemetry` generates the series for any component not
mapped to a published package. Nobody points a hackathon entry at their
production observability stack, and a reviewer should not be asked to.
Every reply names which of the two it is, in an `origin` field.

The generated series is not noise. It carries the diurnal shape real
traffic has — a trough overnight, a peak in the working day — and it is
deterministic, so the same component always produces the same series. Two
people reading one board see the same numbers, and a run can be reproduced
tomorrow. It is anchored to the scale the component declares: a component
stating a 12,000 RPS peak is read at that scale rather than at a generic
per-tier rate.

## Modelled

Availability, recovery time, latency, and cost come from a deterministic
engine running on the capacities the architecture declares. The input and
output fingerprints on every run prove reproducibility. That is not the
same thing as measured production telemetry, and it is not presented as a
prediction about any real system.

Every coefficient the engine uses is a declared assumption, named and
commented in `availabilityModel` and `costModel` in
`src/simulation/engine.ts`, chosen to rank architectures consistently
against one another. They are **not calibrated against measured production
incidents**, and this product does not claim they are. Read the output as a
resilience ranking rather than an SLO: the number that matters is which
future scores better and why, not the absolute figure.

Incident threads are opened from the architecture itself — a database with
no standby, a component that cannot absorb a 1.5x spike, the region
holding the write path. They are not driven by a live alerting feed.

## Where the fixture shapes come from

The shipped example systems are modelled on published engineering
material. The topologies and ratios follow the sources; the absolute
numbers are scaled so a system stays legible on one canvas.

**Live event streaming** follows what Hotstar published about the 2019
Cricket World Cup semi-final at AWS re:Invent 2019 (session CMY302):
25.3M peak concurrent viewers, over 1M requests per second, and 10 Tbps of
egress. The architectural constraint in that talk is the one this fixture
is built around — they do not autoscale into a spike, because an instance
takes about a minute to boot and the scaler reacts in about ninety seconds,
while the audience grows by more than a million people a minute. Capacity
has to be standing before the spike arrives, which is why the fixture's
failure under `traffic_spike` originates at the licence service: every
viewer asks for a licence before the first frame plays, so a resumed
innings arrives as a single burst.

Two things worth recording, because they are widely repeated and wrong. A
figure of "821 million concurrent" circulates for the 2026 T20 World Cup
final; it exceeds India's internet population and is not what the ICC
published, which is 72.5M. A figure of "500,000 orders per minute" is
attributed to Amazon for Prime Day 2024 and does not appear in the AWS
post it is credited to. Neither is used here.

The other fixtures — payment platform, ride-hailing dispatch, AI inference
— are constructed topologies chosen to exercise different failure shapes
(a single write path, a two-sided dependency, a shared read store). They
do not model any specific company's system.
